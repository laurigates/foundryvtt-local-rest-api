# FoundryVTT Module Development with API and External Integration

FoundryVTT offers extensive capabilities for creating modules with API functionality and external server integration through its JavaScript-based architecture, socket.io infrastructure, and comprehensive hook system. The platform supports multiple integration patterns from simple webhooks to sophisticated WebSocket relay architectures, enabling developers to connect external services, create REST APIs, and even potentially integrate Model Context Protocol servers for AI-enhanced gaming experiences.

## Module development architecture provides flexible foundation

FoundryVTT modules follow a structured architecture centered around a manifest file (`module.json`) that defines the module's identity, dependencies, and resources. The standard module structure organizes code into `/esmodules/` for ES6 JavaScript, `/scripts/` for legacy code, `/styles/` for CSS, and `/templates/` for Handlebars templates. **Module initialization follows a predictable lifecycle** through three critical hooks: `init` for early setup and registration, `setup` for pre-world configuration, and `ready` when all game data becomes available. This event-driven architecture allows modules to intercept and extend virtually any aspect of the game system through hooks like `preCreateActor`, `updateActor`, and `renderChatMessage`.

The manifest file serves as the module's blueprint, specifying compatibility ranges, author information, and critically, whether the module requires socket access through the `"socket": true` flag. Modules can declare dependencies on other modules or libraries through the relationships field, ensuring proper load order and compatibility. Best practices emphasize defensive programming with existence checks, graceful fallbacks for optional dependencies, and using official APIs rather than manipulating private properties. **Performance optimization focuses on efficient hook usage**, implementing specific hooks instead of generic ones, and proper memory management through caching strategies that clear on scene changes.

## Creating API endpoints leverages socket.io and custom patterns

FoundryVTT's built-in socket.io v4 infrastructure provides the foundation for creating API-like functionality within modules. By requesting socket namespace access in the module manifest, developers gain access to `game.socket` for bidirectional communication between clients. The platform enforces a naming convention where socket events must follow the pattern `module.{module-id}`, ensuring namespace isolation between modules. **Socket handlers can implement acknowledgment callbacks** for request-response patterns, enabling pseudo-REST semantics over WebSocket connections.

Version 13 introduces a Query System that provides a more structured approach to cross-client communication. Developers can register query handlers in the CONFIG object and invoke them on specific users with timeout support, creating a reliable RPC mechanism. For external access, several architectural patterns have emerged: the WebSocket relay approach used by the Foundry REST API module connects to an external relay server that bridges HTTP REST requests with FoundryVTT's WebSocket protocol, while modules like Palantiri implement JSONRPC 2.0 proxy servers that allow external software to control FoundryVTT through standardized protocols. **The HTTP API module takes a simpler approach**, exposing FoundryVTT's internal API through HTTP endpoints accessible via browser sessions, though this requires active authentication.

## External server connections employ multiple proven methods

Three primary patterns dominate external server integration in FoundryVTT modules. The webhook pattern, widely used in Discord integration modules, implements event-driven outbound communication with rate limiting and queue management to respect API limits. The proxy server pattern, exemplified by DDB-Importer and the REST API module, uses external servers to handle authentication and bypass CORS restrictions, implementing relay architectures that bridge browser limitations. **Browser extension patterns provide enhanced API access**, as seen in DDB-Importer's Chrome extension that manages cookies and enables cross-origin requests that wouldn't be possible from pure module code.

For bidirectional communication, WebSocket connections remain the gold standard. The Foundry REST API module's relay server maintains persistent connections between external clients and FoundryVTT instances, using API keys for authentication and implementing reconnection logic with exponential backoff. Direct HTTP access requires careful CORS configuration, with modules needing to handle preflight requests and credential management. **Network configuration typically requires reverse proxy setup** for production deployments, with specific headers for WebSocket upgrade paths and proper forwarding of the socket.io namespace.

## Existing modules demonstrate diverse integration approaches

The ecosystem includes mature examples of external service integration across multiple categories. Discord modules like Foundry to Discord implement comprehensive chat mirroring with webhook-based architectures, supporting real-time message editing, deletion synchronization, and system-specific content parsing through enricher patterns. The module maintains separate webhooks for different message types and implements sophisticated rate limiting to handle rapid updates without hitting Discord's API limits. **DDB-Importer represents the gold standard for complex service integration**, combining a proxy server for authentication, a Chrome extension for cookie management, and bidirectional synchronization that can both import D&D Beyond content and export Foundry changes back to the service.

World Anvil Integration demonstrates API token-based authentication patterns, using the service's native API for article import while preserving cross-references and maintaining synchronization state. Simple Calendar showcases real-time external synchronization, integrating with weather services and implementing hooks for time-based triggers that other modules can utilize. **For direct API exposure, modules follow two approaches**: HTTP API creates simple HTTP endpoints requiring browser authentication, while Palantiri implements a full JSONRPC 2.0 WebSocket proxy allowing external automation tools to control FoundryVTT programmatically.

## Programmatic game world interaction uses document-based APIs

FoundryVTT organizes all game data around Documents - persistent data structures representing actors, scenes, items, chat messages, and other game objects. The API provides comprehensive CRUD operations through methods like `Actor.create()`, `document.update()`, and `actor.deleteEmbeddedDocuments()`. **Documents support both world-level and embedded operations**, allowing modules to manipulate top-level actors or items embedded within them. The system uses dot notation for nested property updates and special syntax like `-=` for property deletion.

Scene manipulation involves creating scenes with specified dimensions and grid settings, then populating them with token documents that reference actors. Chat messages support various types including in-character messages, whispers, and roll results, with speaker identification and targeting specific users. **Advanced operations leverage the hook system** for intercepting document lifecycle events - pre-hooks can prevent operations by returning false, while post-hooks react to completed changes. Modules can register custom document classes that extend base functionality, adding computed properties and custom methods specific to game systems.

## Security implementation requires multi-layered approach

FoundryVTT implements a tiered permission system with five user roles from None through Gamemaster, each with increasing privileges. Document-level permissions provide granular control with ownership levels from None (no access) through Limited, Observer, and Owner (full control). **Modules must validate permissions before operations**, checking both user roles and document-specific permissions using methods like `canUserModify()` and `getUserLevel()`.

Socket communication security requires validating sender permissions, data structure integrity, and implementing proper sanitization. Input validation should follow defined schemas with type checking, length limits, and range validation for numeric values. HTML content requires sanitization to prevent XSS attacks, removing script tags and event handlers while preserving safe formatting. **API key management for external integrations** should implement time-based expiry, usage tracking, and secure storage using FoundryVTT's settings system rather than plain text. Rate limiting prevents abuse through configurable per-endpoint limits with sliding window algorithms.

## MCP server integration offers AI-enhanced possibilities

Model Context Protocol integration with FoundryVTT is technically feasible through multiple approaches, though no current implementations exist. MCP's JSON-RPC 2.0 foundation aligns well with FoundryVTT's existing WebSocket infrastructure, and the protocol's three core capabilities - Resources for read-only context, Tools for LLM-callable functions, and Prompts for task templates - map naturally to FoundryVTT's document system and API. **A FoundryVTT module could implement an MCP client** that connects to external MCP servers, enabling AI-powered NPC generation, encounter design, and narrative assistance.

Alternatively, FoundryVTT could expose its functionality as an MCP server, allowing external AI systems like Claude Desktop to interact with game data. This would require implementing the MCP protocol's tool and resource definitions, mapping FoundryVTT operations to MCP-compatible interfaces. **The bridge pattern offers a pragmatic middle ground**, using existing modules like Foundry REST API to provide HTTP/WebSocket access while a separate service translates between FoundryVTT's API and MCP protocol. Implementation challenges include real-time synchronization between AI and game state, security considerations for API key management, and performance implications of AI service latency.

## Best practices ensure robust module development

Defensive programming principles mandate checking for existence before accessing game objects, implementing try-catch blocks for external operations, and providing graceful fallbacks when optional dependencies are unavailable. Use official APIs exclusively rather than manipulating internal properties that may change between versions. **Performance optimization requires efficient hook usage**, subscribing to specific events rather than generic ones, implementing caching strategies with appropriate invalidation, and using `Hooks.once` for one-time operations.

Module interoperability demands exposing clean APIs through the module object, using flags for module-specific data storage, and implementing proper namespace isolation. Settings should differentiate between world-scope (shared) and client-scope (per-user) configuration, with appropriate UI exposure based on user roles. **Data handling must respect FoundryVTT's patterns**: use flags for document-specific module data, settings for configuration, and proper cleanup on module unload or scene changes.

## API documentation reveals extensive hook ecosystem

The Foundry API provides over 200 hooks covering every aspect of the game lifecycle. Initialization hooks fire once per session in sequence: `init` for core setup, `setup` after data models configure, and `ready` when game data loads. **Document lifecycle hooks include pre- and post-variants** for create, update, and delete operations on all document types, with pre-hooks able to prevent operations by returning false.

Canvas and rendering hooks enable interaction with the visual game board, from `canvasInit` through `canvasReady`, with specific hooks for token interactions like `hoverToken` and `targetToken`. Application rendering hooks allow modification of any UI element, with specific hooks for actor sheets, chat messages, and other interfaces. **Combat management hooks** track initiative, rounds, and turns, enabling automated effects and turn-based mechanics. The socket API provides emit and on methods for custom module communication, while utility functions handle property manipulation, data merging, and version comparison.

## External API access modules provide ready solutions

Several production modules already provide external API access to FoundryVTT data. The HTTP API module creates simple HTTP endpoints accessible through browser sessions, supporting any Foundry API method with URL parameters. Foundry REST API implements a professional WebSocket relay architecture with API key authentication, providing RESTful endpoints through an external relay server. **Palantiri offers the most sophisticated approach** with a complete JSONRPC 2.0 WebSocket proxy, enabling external automation tools to fully control FoundryVTT through standardized protocols.

For specific service integration, modules demonstrate various patterns: webhook-based for Discord integration supporting real-time mirroring, OAuth flows for services like D&D Beyond requiring user authentication, and API token patterns for World Anvil and similar services. **These modules handle common challenges** including CORS restrictions through proxy servers, rate limiting through request queues, data format transformation between service schemas and FoundryVTT documents, and bidirectional synchronization with conflict resolution.

## Conclusion

FoundryVTT's module development framework provides comprehensive capabilities for API creation and external integration through its socket.io infrastructure, extensive hook system, and flexible document model. The platform's architecture supports everything from simple webhook integrations to sophisticated bidirectional synchronization with external services, with proven patterns demonstrated by existing modules. Security considerations require careful attention to permission validation, input sanitization, and secure credential management, while emerging standards like Model Context Protocol offer exciting possibilities for AI-enhanced gaming experiences. Success in module development comes from leveraging FoundryVTT's official APIs, following established patterns from the community, and maintaining focus on user experience while implementing robust error handling and security measures.
